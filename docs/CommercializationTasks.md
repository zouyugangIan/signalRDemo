# SignalRDemo 商业化升级任务拆解

本文档记录 SignalRDemo 从演示项目升级到商业应用的重点任务。目标不是一次性重写，而是按风险和依赖顺序补齐身份安全、数据持久化、可运维、规模化和桌面交付能力。

## 当前定位

当前项目适合作为 SignalR + Avalonia 学习和演示 Demo。若要商业化，必须优先处理以下差距：

- 身份来自客户端传入的用户名，缺少可信认证和授权。
- 在线用户、房间、文件块均为内存状态，服务重启后丢失，且无法安全横向扩容。
- CORS 允许任意来源并允许凭据，不适合生产环境。
- 缺少消息历史、审计、附件存储、后台管理、可观测性和发布体系。
- macOS 上系统监控数据尚未完整实现。

## 规划原则

- 先做安全和数据边界，再做高级体验。
- 先建立可观测性和交付管线，再承诺稳定性指标。
- 服务端状态尽量外置：数据库保存业务事实，Redis 保存短期在线状态和缓存。
- SignalR Hub 只负责实时通道，业务规则放到应用服务层。
- 桌面端按商业分发标准处理签名、公证、自动更新和崩溃诊断。

## 阶段 0：基础修复和风险清理

### T0.1 修复依赖漏洞告警

目标：处理 `Tmds.DBus.Protocol 0.21.2` 高危漏洞告警。

任务：

- [ ] 定位该包来自哪个 Avalonia 或桌面依赖。
- [ ] 尝试升级 Avalonia 相关包到可消除告警的版本。
- [ ] 如果短期无法升级，记录漏洞影响范围、平台影响和临时风险豁免。
- [ ] 将 `dotnet restore` 和 `dotnet build` 纳入常规验证。

验收：

- `dotnet restore SignalRDemo.slnx` 无高危漏洞告警，或存在明确豁免记录。
- `dotnet build SignalRDemo.slnx --no-restore` 通过。

### T0.2 修复 macOS 监控数据

目标：让截图右侧系统监控在 macOS Apple Silicon 上返回有效数据。

任务：

- [ ] 为 macOS 实现内存使用率读取。
- [ ] 为 macOS 实现网络收发速率读取。
- [ ] 明确当前 CPU 指标是“服务端进程 CPU”还是“整机 CPU”。
- [ ] 在 UI 上标注或调整指标含义，避免误导用户。

验收：

- macOS 上 CPU、内存、入流量、出流量不再长期固定为 `0.0`。
- Linux/Windows 现有逻辑不回退。

## 阶段 1：商业可用底座

### T1.1 身份认证和授权

目标：建立可信用户身份，禁止匿名用户调用核心 Hub 方法。

任务：

- [ ] 接入 OIDC/OAuth2 登录，支持企业身份源扩展。
- [ ] 桌面端保存和刷新 access token。
- [ ] SignalR 连接通过 token 认证。
- [ ] Hub 使用 `[Authorize]` 或策略授权保护。
- [ ] 服务端从 `Context.User` 获取用户 ID 和显示名，不再信任 query string 用户名。
- [ ] 建立角色权限模型：Owner、Admin、Member、Guest。

验收：

- 未登录用户不能连接 Hub。
- 用户不能伪造其他用户名发送消息。
- 房间、私聊、管理动作都有明确授权判断。

### T1.2 数据模型和持久化

目标：将核心业务事实从内存迁移到数据库。

任务：

- [ ] 引入 PostgreSQL 或 SQL Server。
- [ ] 建立用户、组织、房间、房间成员、消息、附件、审计日志表。
- [ ] 使用 EF Core migration 管理 schema。
- [ ] 消息发送成功后写入消息表。
- [ ] 房间创建、加入、离开写入持久状态。
- [ ] 提供消息历史分页接口。

验收：

- 服务端重启后房间和消息历史仍存在。
- 用户重连后能恢复房间列表和最近消息。
- 数据库迁移可在新环境从零执行。

### T1.3 安全边界加固

目标：关闭 Demo 级开放配置，建立生产安全边界。

任务：

- [ ] CORS 改成配置化白名单。
- [ ] 生产环境强制 HTTPS/WSS。
- [ ] 限制 SignalR 消息大小、消息频率和连接频率。
- [ ] 对房间名、用户名、消息内容做长度和格式校验。
- [ ] 日志中避免记录敏感 token、私聊正文和上传文件内容。
- [ ] 为上传接口增加文件大小、扩展名、MIME 类型校验。

验收：

- 非白名单 origin 不能访问生产服务。
- 过长消息、刷屏、异常上传会被拒绝并记录安全事件。
- 开发环境和生产环境配置分离。

## 阶段 2：核心产品能力

### T2.1 消息体验升级

目标：从“实时聊天”升级为“可持续使用的协作消息系统”。

任务：

- [ ] 消息历史分页加载。
- [ ] 未读计数和已读回执。
- [ ] 消息编辑和撤回。
- [ ] @ 提及和通知。
- [ ] 私聊权限和黑名单。
- [ ] 房间公告和置顶消息。
- [ ] 基础全文搜索。

验收：

- 用户重新打开客户端可以看到历史消息。
- 切换房间后未读状态准确。
- 被撤回或编辑的消息在所有在线客户端同步更新。

### T2.2 附件系统

目标：替换内存文件块缓存，支持可靠附件上传和下载。

任务：

- [ ] 引入对象存储：S3、MinIO 或 Azure Blob。
- [ ] 服务端只保存附件元数据和访问权限。
- [ ] 支持分片上传、断点续传和失败重试。
- [ ] 附件下载使用短期授权 URL 或受控代理接口。
- [ ] 集成病毒扫描或内容安全扫描。
- [ ] 增加附件生命周期清理任务。

验收：

- 大文件上传不会导致服务端内存持续增长。
- 用户只能下载自己有权限访问的附件。
- 上传失败后可以重试或恢复。

### T2.3 管理后台

目标：让运营和企业管理员不依赖数据库手工操作。

任务：

- [ ] 用户管理：禁用、重置权限、踢出在线会话。
- [ ] 组织和房间管理。
- [ ] 角色权限配置。
- [ ] 审计日志查询。
- [ ] 服务状态和版本信息展示。
- [ ] 系统配置管理。

验收：

- 管理员可在 UI 中完成常见运营动作。
- 高风险操作写入审计日志。
- 普通用户不能访问管理后台。

## 阶段 3：生产规模和稳定性

### T3.1 SignalR 横向扩容

目标：支持多服务实例部署。

任务：

- [ ] 选择扩容方案：Azure SignalR Service 或 Redis backplane。
- [ ] 在线状态迁移到 Redis，并设置 TTL 和心跳。
- [ ] 房间成员关系由数据库保存，Redis 缓存在线连接映射。
- [ ] 处理多实例下的私聊投递、房间广播和重连恢复。
- [ ] 编写扩容压测脚本。

验收：

- 两个以上服务实例同时运行时，消息投递仍然正确。
- 任一实例重启不会导致全局在线状态长期错误。
- 达到目标并发连接数和消息吞吐指标。

### T3.2 可观测性

目标：让问题可发现、可定位、可量化。

任务：

- [ ] 接入 OpenTelemetry traces、metrics、logs。
- [ ] 记录连接数、消息吞吐、失败率、重连次数、上传失败率。
- [ ] 记录 P95/P99 Hub 方法耗时。
- [ ] 接入 Prometheus/Grafana、Azure Monitor 或同等平台。
- [ ] 建立告警：错误率、连接数异常、消息延迟、数据库异常、存储异常。

验收：

- 能从一次用户报障定位到连接、Hub 调用、数据库和存储链路。
- 关键指标有仪表盘和告警阈值。

### T3.3 可靠性工程

目标：降低生产事故概率，并让故障可恢复。

任务：

- [ ] 健康检查拆分为 `/health/live` 和 `/health/ready`。
- [ ] 支持优雅停机和连接迁移提示。
- [ ] 数据库备份和恢复演练。
- [ ] 幂等消息 ID，避免重试导致重复消息。
- [ ] 引入后台任务队列处理通知、扫描、清理。
- [ ] 编写压力测试、断网重连测试和长连接稳定性测试。

验收：

- 发布或重启不会造成大面积消息丢失。
- 有可重复执行的恢复流程。

## 阶段 4：桌面商业交付

### T4.1 跨平台安装包

目标：让用户以标准方式安装和启动客户端。

任务：

- [ ] macOS 输出 `.app` 和 `.dmg`。
- [ ] macOS 完成 Developer ID 签名和 notarization。
- [ ] Windows 输出安装包并完成代码签名。
- [ ] Linux 输出 AppImage、deb 或 rpm。
- [ ] 建立发布版本号和渠道策略：stable、beta、internal。

验收：

- macOS 首次打开不出现未认证开发者拦截。
- Windows 安装包签名有效。
- 发布产物可从 CI 自动生成。

### T4.2 自动更新和崩溃诊断

目标：降低客户端维护成本。

任务：

- [ ] 实现自动更新检查。
- [ ] 支持强制升级和灰度升级。
- [ ] 客户端崩溃日志收集。
- [ ] 增加用户可导出的诊断包。
- [ ] 客户端配置远程下发。

验收：

- 客户端能从旧版本升级到新版本。
- 发生崩溃后能定位版本、平台、异常栈和最近操作。

### T4.3 产品体验和合规

目标：达到企业用户日常使用和采购审查要求。

任务：

- [ ] 国际化和本地化。
- [ ] 可访问性检查。
- [ ] 网络异常和重连状态优化。
- [ ] 空状态、加载状态、错误状态统一。
- [ ] 数据导出、数据删除和保留策略。
- [ ] 隐私政策、服务条款、许可证页面。

验收：

- 常见异常状态有明确反馈和恢复路径。
- 企业客户可以审查数据保留和隐私策略。

## 建议迭代顺序

1. T0.1、T0.2：先清掉当前明显风险和截图可见问题。
2. T1.1、T1.2、T1.3：建立商业化底座，这是后续所有功能的前提。
3. T2.1、T2.2：补齐用户真正会依赖的消息和附件能力。
4. T3.1、T3.2、T3.3：进入生产部署和规模化。
5. T4.1、T4.2、T4.3：完成桌面客户端商业交付。
